附录 Y　实证探针集：软件项目与文献网络

本附录汇总三次真实、可复现的数据探针，并给出方法学自检。三次结果的对比（一个被支持、一个不可判、一个方向相反）是本书从"自洽理论"走向"实证对话"的最完整记录。所有脚本与结果文件均在仓库中。

Y.1　软件项目探针：量度决定结论

设计（脚本 analysis/linux_kernel_probe.py） 假设：跨多个子系统（top-level 目录）的改动，比单子系统改动更慢被接受。
两个仓库 × 两种量度：torvalds/linux（commit 模式，author→committer 时延）；nodejs/node（pull 模式，PR merge latency）。
统计：Spearman r+p（scipy）、Mann–Whitney U、Cliff's delta、bootstrap 中位数差 95% CI。
复现：python analysis/linux_kernel_probe.py --n 200。

图 Y.1　两个软件项目的实证探针。同一假设：在 Linux 的 commit 量度上不被支持（CI 跨 0），在 nodejs/node 的 PR 量度上被强支持（p=0.0003，CI 不含 0）。
最重要的教训：先前那个"否定结果"是量度的人工产物 上一个版本（附录 W.6）报告了 Linux 探针的否定结果，并归因于"时延代理被污染"。升级后的双仓库对照确认了这个归因：同一个假设，换一个干净的量度（PR merge latency ≈ 审阅时延）后，被强支持。
结论：（1）"跨子系统改动更慢"这一假设在 PR 型项目上成立；（2）Linux 的否定结果不应读作"假设被证伪"，而应读作"commit 量度测不准"。这正是"量度有效性"必须先于"结论"的方法学原则。

Y.2　文献网络探针：学科分裂的朴素预测不被支持

设计（脚本 analysis/arxiv_crossfield.py） 假设（来自第 12 章）：若学科走向分裂，则论文的跨领域耦合（arXiv cross-listing）应随时间下降或停滞。
操作化：在 1995/2000/2005/2010/2015/2020/2023 各抽样 300 篇，统计每篇的 arXiv 分类数（primary + cross-list）。
复现：python analysis/arxiv_crossfield.py --per-year 300。

结果判读：朴素预测被反驳（方向相反） 跨分类论文占比持续上升（0.17 → 0.54），而非按"学科分裂"的朴素预测下降。
因此，第 12 章的"分裂"主张在这一操作化下不被支持，甚至被反向证据挑战。两种可能：
（a）分裂主张错：跨领域耦合其实在增强（"收敛"而非"分裂"）；
（b）量度测不准：cross-listing 是作者自选标签，且 arXiv 类别数随 cs 领域扩张而增加——它测的是"声明式的跨领域"，不是"实际的知识传递（引用耦合）"。
本书倾向于（b），但这需要一个引用层面的量度来裁决（登记为 O36）。在裁决之前，第 12 章的分裂主张应被视为未被实证支持。

Y.4　方法学自检

自检 Y.1　量度有效性（这是最重要的自检） Linux commit 量度：author→committer 的差，混淆了"评审延迟 / 排队延迟 / 维护者树合并延迟"三件事，不能单独归因于"架构缺口"。
nodejs PR 量度：created→merged 更接近"审阅 + 排队"，但同样包含"作者响应延迟"。
arXiv cross-list 量度：作者自选标签，且受领域构成变化污染。
结论：三次探针的量度都不完美；换量度会换结论——这是关于"框架可检验性"的最诚实发现。
自检 Y.2　实验质量自评 数据来源：A（GitHub/arXiv API 公开可复现）；样本统计：B（已给 p 值/CI，但 Linux 跨子系统样本仅 9）；量度选择：C（可能选错量）；对照设计：C（无随机对照，仅两仓库）；因果推论：B−（有支持但混淆多）。
读作："初步勘探"，而非"最终判定"。与其他三例（LTCM/NCLB/AlphaFold）的事后分析相比，它是本书第一次"事前预测 + 事后检验"。
自检 Y.3　因果推论的局限 软件探针最多支持"跨子系统改动在 PR 型项目中更慢"——但不能区分这是（i）架构复杂性、（ii）多维护者分权治理、还是（iii）跨模块改动的天然稀缺。要区分，需要 PR 型项目的对照与分层设计（O35）。arXiv 探针最多支持"声明式跨领域标签增加"——不能支持"知识传递增强"。
自检 Y.4　为什么先做软件与文献 选择它们，因为数据最公开、周期最短、可复现成本最低。但这个选择有"赌徒逻辑"的风险：若在这里失败，我们可能误判框架——而失败也许只源于量度选错（如 Y.1 所示）。因此正确的做法不是"单次赌注"，而是"探针集 + 分层对照"——这正是本附录的形态。

Y.5　下一步

三个可执行方向 O35（软件，修订）：原假设"跨子系统更慢"过于笼统。三个候选解释——（i）架构复杂性（K_comp/K_desc）/（ii）多维护者分权（代理权力）/（iii）跨模块改动天然稀少。设计分层对照（核心 vs 驱动、内部 vs 外部贡献者、补丁大小分层），用 PR 型项目做对照，以区分三者。
O36（文献，新）：用引用层面的量度（OpenAlex/Crossref）替代 cross-listing，检验"跨领域引用比例"而非"标签数"——这才是"知识传递"的可测代理。
O37（多源三角）：同一领域同时用三类数据（代码 / 文献 / 事件）交叉验证，看三角诊断是否稳健。
本附录的诚实定位 三次探针没有验证框架，也没有推翻框架——它们做的是另一件更有用的事：展示框架的哪些假设可以被真实数据检验，以及检验的结果如何强烈依赖量度选择。这是本书能给出的关于"实证"的最诚实结论。
