附录 W　四个失败的深度案例：框架何时失效

附录 S 给出三个边界案例，但它们多为"让出顶点后的代价"。本附录更进一步：用框架对四个标志性失败做"事后诊断"，并逐一检查——框架预测对了吗？哪里错了？为什么？这是对第 21.7 节"L2—L3 预测力"的实证检验，也是对附录 U.4"失败分类"的历史验证。

阅读约定 每个案例分四段：（1）框架会怎么诊断（事前）；（2）实际发生了什么；（3）诊断匹配吗；（4）为什么（不）匹配。
等级采用附录 A.11 的细化制（B1—B3 / C1—C3），逐案标注：NCLB 有多个同行评议政策研究支持（B1）；Linux 有公开仓库数据但解释存争议（B2）；LTCM 基于大量公开数据但归因仍有分歧（B3）；AlphaFold/GPT 的新配置为推测（C1）。本书不宣称这些诊断优于领域内更完整的解释。

W.1　LTCM（1998）：C+A 让出 T 的潜伏失效

（1）框架的事前诊断 长期资本管理公司（LTCM）选择 C+A：完备的定价/套利模型（C）+ 高度可组合、可加杠杆的头寸（A）。让出 T——模型内部的结论无法无损传递到"市场—流动性—系统性传染"的跨尺度整体。
预测：若 t（跨尺度传递）低，则单个头寸看似稳健、组合层看似分散，但跨到系统层会同时失效；失败形态应为T 型（潜伏失效），而非 C 型阈值崩溃。

（2）实际发生了什么。1998 年俄罗斯违约引发全球流动性收缩，LTCM 的"分散"头寸同时亏损（相关性在压力下趋 1）；模型假设的独立性与流动性均失效；美联储组织救助以避免系统性传染。

（3）诊断匹配吗？部分匹配，但分类需要修正。框架事前说"T 型潜伏失效"，这被抓到了——问题的确是"局部完备/可组合，跨到系统层不传递"。但 AI 建议把它当作"C 型阈值崩溃"来检验，这个预期本身是错的：LTCM 的 C 并不弱（模型极精），它让出的是 T。因此这个案例验证的是 T 型，而不是 C 型。

（4）为什么诊断"部分失效" 框架抓住了正确的被让出的顶点（T），但没有预测到失效的时点与触发条件（俄罗斯违约 + 流动性）。这正是第 21.7 节所说的"L2 而非 L4"：框架能说"会出现 T 型缺口"，不能说"何时、由什么触发"。这也是"框架何时失效"的第一个实证证据：它分类失效形态，但不预测失效时刻。
第四个陷阱：框架与领域常识的分类冲突 W.1 中，三角给出的诊断是 T 型，而金融学通常把 LTCM 归为"C 型"（模型风险）或"流动性冲击"。这不是框架失效，而是两个分类系统的坐标不同：
金融学按"触发机制"分类（宏观冲击 → 流动性枯竭）；三角按"被让出的顶点"分类（微观的跨尺度不可加）。
两者都不错，只是回答不同问题。框架的价值不在于比金融学更"正确"，而在于提供了第二种视角——它把"哪个性质被让出"单独拎出来。承认分类冲突，正是框架不宣称"唯一真理"的证据。

W.2　美国教育标准化运动（2001—2015）：双极摆动的可逆性

（1）框架的事前诊断 第 8.7 节说教育倾向双极摆动（A+T ↔ C+A），而非三阶段循环。
预测：2001 年《不让一个孩子掉队》（NCLB）把系统推向 A+T（标准化测试 + 问责），让出 C（个体发展）；若双极模式成立，则应出现反向压力，并在若干年内摆回。

（2）实际发生了什么。NCLB 强化标准化测试与学校问责，压缩了课程多样性与个体发展（C 被让出）；随后出现广泛反弹（"应试化"批评、家长与教师抵制），2015 年《每个学生成功法》（ESSA）显著放权，弱化联邦测试问责——系统摆回。

（3）诊断匹配吗？匹配。框架预测了"双极摆动"的形态与可逆性，现实中确实先摆向 A+T 又摆回。这是本书少见的"形态预测被历史支持"的案例之一。

（4）为什么匹配，以及它的局限 匹配的原因：教育系统缺少"危机—重启"的可能（不能承受 C+T 的高成本），因此只能在两个顶点间摆动——这正是第 11.8 节"风险承受度决定模式"的一个实例。
局限：框架预测了"会摆回"，但没预测"何时摆回、摆多久"（NCLB 到 ESSA 约 14 年）。再次是 L2 而非 L4。

W.3　Linux 内核（2010s）：A+T 下的深度创新约束

（1）框架的事前诊断 Linux 内核的开发模式接近 A+T：高度模块化、多贡献者、长期持续维护（A + T）。让出 C——难以进行需要全局架构一致性的深度重构。
预测：跨越多个子系统的大架构改动会异常困难（因为每个维护者只对自己的模块负责）；而局部模块改进会繁荣。

（2）实际发生了什么。Linux 内核在局部驱动、性能、文件系统上持续繁荣；但需要跨子系统的大改动（如 Rust 集成、核心调度重构、维护者结构改革）反复陷入长期争论；维护者倦怠与"巴士系数"问题被广泛讨论。

（3）诊断匹配吗？匹配。"局部繁荣 + 全局重构困难"正是 A+T 让出 C 的预期形态。

（4）为什么匹配，局限在哪 匹配：模块化（A）与长期维护（T）确实以"全局架构完备性（C）"为代价。
局限：这个诊断是"事后可读性强、事前预测弱"——它不能事先告诉你"哪个具体重构会卡住"。而且它与"分布式协作天然慢"的常识解释难以区分——这正是第 21.6 节自检担心的"框架太灵活、容易事后解释"的风险。

W.4　AlphaFold 与 GPT 对学科的冲击：K 扩大后的重新选择

（1）框架的事前诊断 新技术会扩大某些领域的 K（如 K_comp），从而使可达域 R(K) 扩张，迫使系统重新选择顶点。
预测：结构生物学（AlphaFold）与大量文本/代码领域（GPT）会出现配置重排——原先可行的 C+A 或 C+T 因 K 扩大而移动。

（2）实际发生了什么。AlphaFold 大幅降低蛋白质结构预测成本，改变了结构生物学的分工（实验结构测定与计算预测的边界重画）；GPT 改变了写作、编程、教育等对"可组合文本产出"的依赖。

（3）诊断匹配吗？部分匹配，但过于笼统。框架正确预测了"会重排"，但没有预测"重排到哪个新配置"。

（4）为什么"部分失效" 框架对"K 扩大 → 可达域扩张"是方向性正确的（O2/O28）；但它无法预测具体的重排结果，因为那取决于领域特有的机制（哪些环节被 AI 替代、哪些未被替代）。这印证了第 2.3 节的开放问题 O28（K 的维度耦合）与第 21.7 节的"L2 而非 L4"。

自检 W.1　为什么三分类总是匹配：真验证还是逻辑枚举 既然任何失败都能被分到 A / C / T 型之一，"形态匹配 4/4"可能有两种解释：
（1）真验证：三分类是必要且充分的——它确实抓到了失败的结构；
（2）逻辑枚举：三分类只是一个"穷举"——任何失败都能贴上一个标签，因此没有预测力（类似"托勒密式的救援"）。
四个案例都被成功分类，但无法区分（1）与（2）。三个"理论上"的区分条件（找无法分类的案例 / 找混合型 / 从 K 结构证明穷举）都很难完成——尤其是第一个，它若成功反而是框架的坏消息。因此，本节把它们改写为可执行的实验设计：

实验 1（对标框架对比，1—2 年）：取 100+ 公开失败案例，分别用三角与两个对标框架（如 Normal Accident Theory、Black Swan 分类）做事前诊断；失败阈值：三角对失效时点/触发的预测准确度不优于对标。
实验 2（边界案例设计，6—12 个月）：人工构造有限 K 系统，刻意制造分类边界；失败阈值：成功构造出"无法清晰分类"或"稳定混合型"的系统。
实验 3（多解释竞争，1—2 年）：对著名失败（如 1998 LTCM、2008 危机）用三角与三个替代解释（技术变革 / 领导更替 / 外部冲击）各自做事前诊断；失败阈值：三角的预测准确度显著低于替代解释。

升级规则：若三个实验都支持三角，O34 可升级为 B 级；若任一失败，O34 将清楚地指出框架在哪个维度失效。本书无法完成这些实验，因此"4/4 匹配"应被读作"尚未发现反例"，而非"已证明充分"。［登记为开放问题 O34］
本附录的三个结论 （1）框架的实证强度：在"失效形态与方向"上匹配 4/4（2 高 2 部分）；在"失效时点与新配置"上匹配 0/4——这精确地刻画了 L2—L3 预测力的边界。
（2）失败分类的验证：U.4 的三分类（缓慢退化 / 阈值崩溃 / 潜伏失效）在 LTCM（T 型）与 Linux（A 型）上有实例；但 LTCM 的分类与常识预期（C 型）相反，说明"事先分类"本身很难。
（3）框架何时失效：当问题需要具体时点、触发条件或新配置时，框架失效；当问题只要失效形态与方向时，框架可用。建议使用者据此决定是否采用本框架。

W.6　实证探针（第一次执行）：Linux 内核

本节是本书第一次真正执行的可复现实证探针，而不是事后叙述。它同时给出一个否定性结果——按本书纪律，否定结果与肯定结果同等重要。

探针设计（脚本 analysis/linux_kernel_probe.py） 对象：torvalds/linux（GitHub API 实时抓取）。
假设（来自 W.3）：跨多个子系统（top-level 目录）的改动，比单子系统改动更慢被接受（C 型架构缺口）。
操作化：取 200 个非合并提交；记录改动的 top-level 目录数；以 committer.date − author.date 作为"补丁从撰写到落地"的时延代理；检验 Spearman 相关与分桶中位数。
可复现：python analysis/linux_kernel_probe.py --n 200。
执行中遇到的第一个发现：内核的 GitHub PR 被禁用 对 torvalds/linux 调用 GitHub /pulls 返回 404——内核不使用 GitHub Pull Requests，而走邮件列表。这本身就是 W.3 诊断的一个旁证：内核的治理是 A+T（模块化 + 长期维护），其协作机制（邮件列表）与平台化的 C+A 模式不同。因此探针改用 commit 历史。

图 W.1　Linux 内核实证探针。跨子系统改动占比极低（4.5%）；"目录数—时延"相关为弱负（−0.12），不支持"跨子系统更慢"的假设。
结果判读：假设未被支持（首要结论） （1）"局部繁荣"被支持：95.5% 的提交只触及一个子系统——与 A 型诊断（模块化 → 局部繁荣）一致。
（2）"跨子系统更慢"未被支持：相关系数为弱负（−0.12），且跨子系统样本仅 9 个——无论方向还是显著性都不支持 W.3 的 C 型缺口预测。
（3）因此，W.3 的诊断在这一操作化下"半通过"：形态（局部繁荣）成立，机制（跨子系统延时）不成立或不显著。这与表 W.1 的"形态匹配、细节缺"一致，但这里更严格：连方向都相反。
为什么可能失败（诚实的归因），以及下一步 （a）时延代理被污染：内核中 95% 提交的作者≈提交者（维护者自提），gap 主要反映补丁"年龄"而非评审时延。
（b）跨子系统改动被"打包"：tree-wide 变更常以维护者树的合并提交出现，在非合并提交样本中几乎看不到。
（c）正确的检验目标可能不是"时延"，而是"被拒绝/被退回的比例"或"review 轮数"——那需要邮件列表（lore.kernel.org）数据。
下一步（登记为 O35）：改用 lore.kernel.org 的 patch 序列，测量跨子系统补丁的收编轮数与退回率，而非 commit 时延。
