X.2　目标的工具：三角诊断套件

目标产物（开放实现） 输入：一个系统的描述（文本 + 可用的时间序列 + 代理人结构）。
输出：
  · 多尺度的 (c, a, t) 读数（附置信区间与等级）；
  · 被让出的顶点的定位与依据；
  · 失效阈值/形态的估计；
  · 一张可导出的权衡矩阵与降级预案（对齐附录 G/H）。
关键要求：每个输出都带证据等级与证伪条件——工具不得比理论更自信。

X.4　学习挑战：跨领域外推

最大的技术难点 从"系统描述"到"坐标读数"的映射，需要把一个领域学到的模式外推到另一个领域。但按第 2 章，不同领域的 (K_desc, K_comp, K_res) 受限分量不同，直接外推风险很高（第 12.5 节的 1/3 缺口就是"离散到连续外推失败"的实例）。
因此工具的合理设计是"分层"的：硬核（可算）→ 模式识别（半自动）→ 领域校准（人工）。不做"一键诊断"的许诺——那会违反第 23.6 节的自反诚实（框架本身让出 T）。

X.4b　三个领域的快速验证路线（优先序：软件 → 医疗 → 教育）

X.4 说跨域外推风险高；但有些领域的验证其实很快。本节给出三条按可行性排序的路线——先从最可行的开始。

X.4.1　软件领域（可在 1 年内执行，A 级数据） 数据源：Linux 内核及 Apache/Node.js 等大型开源仓库（贡献历史、依赖图、缺陷记录）。
验证目标：（a）A 型诊断——模块化下的"局部繁荣"是否表现为贡献分布的长尾与局部集中？（b）C 型缺口——跨子系统大改动（涉及多个 maintainer）的处理周期是否显著长于局部改动？
可行性：A 级（数据公开、方法清晰、可复现）。建议优先执行。
已执行（两次，附录 W.6 与 Y.1）：内核 GitHub PR 被禁用（改用 commit 历史）；Linux 的 commit 量度不支持"跨子系统更慢"（r=−0.10, p=0.17），但 nodejs/node 的 PR 量度强支持（r=+0.25, p=0.0003, CI 不含 0）——结论依赖量度。下一步见 O35。
X.4.2　医疗领域（可在 2—3 年内执行，B 级数据） 数据源：电子病历 + 临床试验登记 + 药物获批数据。
验证目标：（a）急症（C+T）与慢病（A+T）的多尺度选择是否可从数据中区分？（b）F9（分层标志物边际增益递减）是否在现有队列上成立？
可行性：B 级（受隐私限制，需数据共享协议）。
X.4.3　教育领域（需特殊设计，C 级数据） 数据源：学习管理系统 + 学生成绩纵向数据。
验证目标：（a）NCLB/ESSA 的摆动是否真的由"风险承受度"驱动？（b）个性化教育能否同时满格 C+A？
可行性：C 级（需教育部门合作、政策受限、周期长）。
为什么要给出这个排序 它把附录 X 从"说方向"变成"指出最容易的第一步"。软件领域是唯一数据全公开、方法最清晰、周期最短的验证场——若三角在软件上被证伪，其他领域的验证就不必做了。这与第 21.8 节 F7（软件涌现缺陷）相互印证：F7 正是这条路线上的第一个可检验预测。

X.5　一个最小可行版本（MVP）

  1. 第一步：把附录 G 的权衡矩阵做成可填写的结构化文件（YAML/CSV），带等级字段。
  2. 第二步：接入附录 K 的案例库与 data/*.csv，自动生成坐标读数与比值。
  3. 第三步：对每个读数检查是否满足适用范围（第 23.5 节）并标注。
  4. 第四步：输出降级预案（对齐第 18 章）与登记条目（附录 E 格式）。
  5. 第五步：保留人工校准环节——工具只做"提醒与核算"，不做"判断"。

邀请。任何读者都可基于上述五步实现并开源；本附录不提供现成代码，只提供接口约定，以免把一个 C 级的框架过早固化成"看起来权威"的软件。这与本书"框架先于工具"的次序一致。
